# The demo form

The form behind **Try a demo form** on the landing page. Public, LLM-backed, and
the first thing a visitor touches — so it is the one form where a failure costs
a customer rather than a response.

- **Live at** `/f/how-you-use-forms`
- **Authored in** `tooling/demo-form/` (`index.ts` for the form, `knowledge.ts`
  for what the agent may say about chatform)
- **Published by** `tooling/seed-demo-form.sql`, generated by `pnpm gen:demo`
- **Linked from** `hero.tsx`, gated on `NEXT_PUBLIC_DEMO_FORM_SLUG`

## Kill it

If it starts costing money, or says something it should not:

```sql
UPDATE forms SET status = 'draft' WHERE slug = 'how-you-use-forms';
```

`GET /p/forms/:slug/config` 404s immediately. No deploy, no rebuild. The hero
pill still renders — it is compiled in — but it lands on a "form not found"
page, which is the right trade against leaving a runaway form open. To remove
the pill as well, clear `NEXT_PUBLIC_DEMO_FORM_SLUG` and `pnpm deploy:web`.

Bring it back with `status = 'published'`.

## Watch what it costs

Every response is a real model conversation billed to the owner's organization,
against the **same monthly buckets as their real forms** — `responses_ceiling_per_month`
and `ai_conversations_per_month`. Crossing the AI cap degrades *every* form in
that org to deterministic template phrasing, not just this one.

The guards, in the order they bite:

| Guard | Value | Where |
| --- | --- | --- |
| `closeRules.maxSubmissions` | 2000 | the hard ceiling — turn this down first |
| `agent.guardrails.maxTurns` | — | not authored; taken from the plan at runtime |
| `agent.sessionTokenBudget` | — | not authored; taken from the plan at runtime |
| `agent.responseMaxTokens` | 320 | per turn |
| session opens | 8/min per IP | `RATE_LIMIT_P_START` |

Spend per org is in `ai_generations`, and the admin console at `/admin` reads it.

## Change it

The definition is the source of truth. **Do not edit this form in the builder** —
the next seed overwrites `working_schema` without warning.

1. Edit `tooling/demo-form/`.
2. Bump `DEMO_REVISION` in `tooling/demo-form/index.ts`. A published version is
   immutable, so a change ships as a new one; `pnpm gen:demo` refuses to write
   otherwise and names the number to use.
3. `pnpm gen:demo`, commit the regenerated SQL, then `pnpm seed:demo:remote`.

## Set it up somewhere new

```bash
pnpm gen:demo && pnpm seed:demo          # local; --remote for production
```

**Read the trailing `SELECT`.** The organization is resolved by joining `members`
on `DEMO_OWNER_EMAIL`, so if that address owns no organization in the database
you are pointed at, the insert matches no rows and the whole file succeeds having
done nothing. One row means seeded; no rows means look again.

Two things after that, and skipping either is the classic "it seeded but the gate
is missing":

1. **The owning org must be on Business.** `requireAuth` is a Business feature,
   and `clampForRuntime` silently switches it off otherwise — leaving an ungated
   LLM open to the internet with no error anywhere. Comp it through
   `POST /api/admin/accounts/:orgId/plan` with **`months: null`**: a timed comp is
   written `status: 'canceled'` and, when it lapses, ungates the form exactly the
   same way.
2. **Bust the entitlements cache**, or wait up to 300 seconds:
   ```bash
   pnpm --filter @repo/api exec wrangler kv key delete --binding KV_CONFIG "ent:<org_id>" --remote
   ```

Confirm with:

```bash
curl -s https://api.chatform.in/p/forms/how-you-use-forms/config | jq .requireAuth
```

`null` means the comp or the cache bust did not land. It should be an object.

3. **Wait one cron tick for the knowledge base.** The demo's knowledge is no
   longer part of the form document — it is `knowledge_sources` rows, seeded
   `status = 'pending'`, because seed SQL is applied by `wrangler d1 execute`,
   which has no Workers AI binding and therefore cannot embed anything. The
   ingest sweep on the five-minute cron picks them up and indexes them.

   So immediately after a fresh seed the agent has a knowledge base that is not
   searchable yet, and will politely deflect every product question. That is the
   sweep not having run, not a broken form. Check before concluding otherwise:

   ```bash
   pnpm --filter @repo/api exec wrangler d1 execute chatform --remote \
     --command "SELECT status, COUNT(*) FROM knowledge_sources WHERE form_id = 'frm_demo00001' GROUP BY status"
   ```

   Every row `ready` means retrieval is live. Any row `failed` carries a readable
   reason in its `error` column. Note this needs the org on **Pro or above** —
   `agent_knowledge` is a Pro feature and `SessionDO` re-checks it per session,
   so a lapsed comp turns the agent back into one that knows nothing. The
   Business comp above covers it.

Locally you also need `NEXT_PUBLIC_GOOGLE_RESPONDENT_CLIENT_ID` in
`apps/web/.env.local` and `http://localhost:3000` in the chatform-respondent
OAuth client's authorised origins, or the sign-in card degrades to "not
available" and the form cannot be completed past question three.

## What it deliberately does not have

- **Turnstile.** `settings.captcha.enabled` is `true` and currently inert:
  `TURNSTILE_SECRET_KEY` is not deployed, and `open-session.ts` skips the check
  without it. Do not push that secret — the web client never sends a token, so
  every existing customer form would start refusing with `captcha_required`.
  It stays `true` so that the day the client is wired, this form is covered
  without a republish. The real protection is the sign-in gate, `onePerIdentity`,
  and the IP limits on `/p`.
- **A payment or scheduling block.** Payments are recorded rather than verified
  and scheduling is a hand-off, so neither can be exercised honestly in a demo
  with nothing to buy and no calendar behind it.
- **Notification emails.** `maxSubmissions` of them would arrive. Read the
  results tab.
